# daily — 작업 요약

Claude Code: `/daily` · Codex: `$daily` — 둘 다 **이 저장소(wf) 루트에서** 연 세션에서 쓴다. 아래 명령은 전부 루트 기준 상대 경로다.

오늘 만들어진 git 커밋을 읽어, **사내 보고용 작업 요약과 갱신된 진척도를 대화에 바로 출력**한다. 요약은 파일로 저장하지 않는다 — 기록으로 남는 것은 `progress.md` 의 진척도뿐이다.

최종 출력은 항상 두 블록이다.

```
<일일 업무 일지에 옮겨 적을 작업 요약>   ← §5

---

<오늘 갱신된 진척도 전체>                 ← §6
```

## 독자

**개발 용어를 조금 아는 비개발 관리자다.** 이 사람은 배포·빌드·API·서버·캐시·테스트가 무엇인지는 알지만, 이 저장소를 열어본 적이 없다. 그래서 두 가지가 동시에 필요하다.

- **업계 일반 용어는 살린다.** 배포·빌드·CI·API·캐시·도메인·사이트맵·회귀 테스트는 풀어 설명하지 않는다.
- **이 저장소 안에서만 통하는 이름은 전부 뺀다.** 훅·스킬·툴링 이름, 파일 경로, 코드 심볼, 커밋 해시, `scope` 는 독자에게 아무 의미가 없다(§4).

판정은 한 문장으로 한다 — **저장소를 열어봐야 아는 말인가?** 그렇다면 그 이름 대신 역할을 쓴다.

## 흐름

### 1. 커밋 수집

이 저장소는 프로젝트 코드가 아니라 **프로젝트 저장소들의 mirror(`repos/*.git`)** 를 모아둔 곳이다. 커밋은 `git log` 를 직접 치지 말고 `wf daily` 로 모은다 — 등록된 모든 저장소를 fetch 한 뒤, `config.json` 의 작성자 이메일로 쓴 커밋만 골라 저장소 → 브랜치 → 커밋 순으로 출력한다.

```bash
node wf.js daily            # 오늘
node wf.js daily yesterday  # 어제
node wf.js daily -7..today  # 최근 1주 (A..B 범위, -N = N일 전)
```

출력 구조: 머리에 작성자·커밋 수·**제품 목록**(`config.json` 의 `products` 이름 전체), 이어서 `## <저장소>` → `### <브랜치>` → 한 커밋당 `- \`해시\` 시각 [제품명] 제목 (+추가/-삭제)`, 그 아래 `  - 변경 파일 목록`, 본문은 `  > ` 인용 줄. 맨 끝 `## 진척도` 는 `progress.md` 내용이며 §6 에서 쓴다.

`[제품명]` 태그는 `wf` 가 `config.json` 의 `products` 규칙(커밋 scope 우선, 없으면 변경 파일 경로)으로 붙인 것이다. 경로로 여러 제품에 걸치면 `[A · B]` 처럼 이어 붙는다. 등록된 저장소가 없거나(`등록된 저장소가 없습니다`) 작성자 필터가 비어 있으면 요약을 시작하지 않고 README 의 설정 절차를 안내한다.

**본문(`>` 줄)을 먼저 읽는다.** 제목이 what, 본문이 why 인 커밋이면 대개 본문만으로 요약이 나온다. 그래도 무엇을 왜 했는지 모호하면 변경 파일 목록을 보고, 그래도 부족하면 mirror 에서 직접 확인한다(bare 저장소라 `-C` 로 경로를 준다):

```bash
git -C repos/<저장소>.git show <해시> --stat
```

정확히 알아야 정확히 요약한다. 커밋이 하나도 없으면(`커밋 0개`) 그 사실을 알리고 멈춘다 — 지어내지 않는다.

**분량은 날마다 크게 다르다.** 커밋이 많다는 것은 묶을 여지가 크다는 뜻이지, 항목을 그 수만큼 만들라는 뜻이 아니다.

### 2. 선별

요약할 가치가 있는 것만 남긴다. 다음은 **빼는 쪽**으로 기운다:

- 머지 커밋, 되돌리기·재커밋 등 순수 git 정리
- lock 파일 갱신, 포맷팅, 오타 한 줄 같은 잡일
- 결과만 있고 의미 없는 임시 커밋(빌드 임시 수정 등)

**같은 회차 안에서 넣었다 되돌린 것은 순변화만 쓴다.** 도입과 철회가 같은 날 다 있으면 결과적으로 바뀐 것이 없으므로 "넣었다 뺐다" 는 독자에게 노이즈다. 다만 그 과정에서 **남은 것**(늘어난 회귀 테스트, 고정된 케이스, 새로 확인된 사실)은 결과이므로 살린다.

**문서·기록 커밋은 종류를 갈라 본다.** 문서·기록 커밋 비중이 높은 저장소가 있다. 결정이나 실측이 처음 들어간 것은 그 자체가 그날의 작업이므로 남기고, 앞 커밋의 진행 상황을 뒤따라 적은 기록(`~ 완주 기록 추가`, `상태 최신화`)은 별도 항목을 만들지 말고 그 주제에 흡수한다.

작은 커밋이라도 그날의 핵심이면 남긴다. 양이 아니라 의미로 고른다.

### 3. 주제로 묶기

**커밋 1개 = 항목 1개가 아니다.** 관련된 커밋을 하나의 작업 단위로 묶는다. 보통 **세넷**이면 충분하다 — 핵심만 남기고 나머지는 가까운 주제에 흡수하거나 버린다.

**`scope` 는 묶는 기준이 아니다.** 앱이 여럿이라 `scope` 가 앱을 가르기는 하지만, 같은 앱 안에서도 주제는 여럿이다. 실제 기준은 **독자가 아는 단위** — 화면 하나(구성원 소개 페이지), 또는 목적 하나(배포 자동화·자동 검사·보안 점검)다. 반대로 앱 코드 커밋과 도구 커밋이 같은 목적으로 함께 움직였다면 `scope` 가 달라도 한 주제다.

### 4. 내부 이름을 역할로 바꾸기

**이 단계가 이 스킬의 핵심이다.** 커밋 메시지는 저장소를 아는 사람끼리 쓴 글이라 내부 이름이 그대로 들어 있다. 지우기만 하면 문장이 무의미해지므로 **그 이름이 하는 일로 바꿔 쓴다.**

| 커밋에 있는 말                                                     | 보고용                                   |
| ------------------------------------------------------------------ | ---------------------------------------- |
| `block-secrets` 훅                                                 | 민감정보 유출 차단 검사                  |
| `docs-check`                                                       | 문서 링크 검사                           |
| `PreToolUse` 훅 / 턴 종료 훅                                       | 작업 도구 실행 전(후) 자동 점검          |
| `systemMessage`                                                    | 작업자 알림                              |
| heredoc 본문                                                       | 명령어에 이어 붙인 입력                  |
| EPIPE / 정규식 / 종료코드                                          | 파이프 오류 / 검사 규칙 / 실행 결과 신호 |
| `turbo.json` 에 env 선언                                           | 빌드 설정에 환경변수 전달 선언           |
| `/settings` 라우트                                                 | 설정 화면                                |
| `## <저장소 이름>` (wf daily 출력의 저장소 구분)                    | 독자가 아는 제품명 — 커밋 앞 `[제품명]` 태그 |
| `fix(hooks)` · `scope(ci)` 등 커밋 접두                            | (버린다 — 독자에게 의미 없다)            |

**제품명은 커밋 앞의 `[제품명]` 태그를 쓴다.** 태그는 `config.json` 의 `products` 규칙에서 오며, 사람마다 저장소·제품이 다르므로 이 스킬에는 표를 두지 않는다. 처리 규칙:

- 태그가 하나면 그 이름이 제품명이다. 모노레포는 저장소 이름이 아니라 scope·앱 경로로 제품이 갈리므로, 같은 저장소 안에서도 태그가 다르면 다른 제품이다.
- `[A · B]` 처럼 여러 제품에 걸친 커밋은 변경 파일을 보고 주된 쪽에 넣는다. 이름에 "흡수" 류 안내가 붙은 규칙(공용 계층 등)은 별도 주제를 만들지 말고 그 변경을 소비하는 앱 주제에 붙인다.
- 태그가 없는 커밋은 저장소 이름을 임시 제품명으로 쓰되, 요약 끝에 **`config.json` 의 `products` 에 규칙을 추가하라고 한 줄로 알린다** (어떤 scope·경로가 안 잡혔는지 함께).
- 진척도(§6) 항목 이름은 이 제품명으로 시작해야 하므로, 태그의 이름을 그대로 쓴다 — 줄이거나 바꿔 부르지 않는다.

저장소가 여럿이어도 제목은 제품명 + 작업 영역으로 쓴다(예: `## 웹 관리자 — 설정 화면`). 저장소가 하나뿐이고 제품이 하나인 날은 제품명을 생략해도 된다.

또한 이렇게 처리한다:

- **커밋 해시·파일 경로·변수명·함수명은 뺀다.** 대체할 역할조차 없으면 그 항목 자체가 독자에게 필요 없는 내용일 가능성이 높다.
- **수치는 살린다.** "회귀 테스트 25건에서 37건으로", "누락 18건 검출" 처럼 커밋에서 확인된 숫자는 보고에서 가장 잘 읽히는 부분이다.
- **라우트는 화면 이름으로 바꾼다.** 개발자용에서는 `/about/people` 이 작업 단위의 이름이지만, 독자는 주소를 모르고 화면을 안다.

### 5. 출력

각 주제를 **제목 + 개조식 항목**으로 대화에 바로 출력한다(파일 저장 안 함).

- **제목**: `##` + **작업 영역을 가리키는 명사구**. 형태를 주제끼리 통일한다 — 하나가 명사구면 전부 명사구다. 주소·파일명·영문 도구명을 제목에 쓰지 않는다.
- **항목**: 한 작업을 짧은 구로 압축하고 **명사형으로 끝맺는다**(`~추가`, `~수정`, `~교체`, `~확대`). 한 주제에 1 ~ 4개.
- **목록 기호(`-`·`*`·번호)를 붙이지 않는다.** 한 줄에 한 항목씩 줄바꿈으로만 가른다 — 보고 양식에 그대로 옮겨 붙이는 글이라 기호가 남으면 손으로 지워야 한다.
- **항목과 항목 사이는 빈 줄로 띄우지 않는다.** 띄우는 자리는 둘뿐이다 — 제목과 첫 항목 사이, 그리고 주제와 주제 사이. 화면에서 항목이 붙어 보이더라도 옮겨 붙는 것은 렌더된 모습이 아니라 원문이므로 원문을 기준으로 한다.
- **무엇이 좋아졌는지가 드러나게 쓴다.** 커밋이 "무엇을 고쳤다" 로 적혀 있어도, 그 수정이 막은 문제나 확인된 결과를 함께 쓰면 독자가 판단할 수 있다. 단, 커밋에 없는 효과를 붙이지 않는다.
- 비슷한 잔작업은 한 항목으로 합친다. 항목이 곧 커밋 목록이 되지 않게 한다.

### 6. 진척도

`progress.md` 는 `## YYYY-MM-DD` 날짜 섹션으로 쌓이는 기록 파일이다. `wf daily` 는 **보고일 섹션**을 찾아 `## 진척도 (날짜)` 아래 붙이고, 그 날짜 섹션이 없으면 직전 날짜에서 **100% 미만인 항목만** 복사해 새로 만든다(완료 항목은 완료한 날 섹션에만 남는다). stderr 에 `섹션 생성` 이 찍힌다.

**오늘 커밋을 근거로 진척도를 직접 갱신한 뒤 출력한다.** 사용자에게 제안만 하고 기다리지 않는다 — 판단 근거는 §1 에서 읽은 커밋이고, 기록은 `progress.md` 가 맡으므로 나중에 되돌릴 수 있다.

1. 요약(§3)의 주제 하나하나를 진척도 항목과 대조한다. 항목 이름은 §4 의 제품명 + 작업 영역이다(`모바일 앱 - 주문 관리 탭 구현`).
   - 기존 항목의 작업이 진행됐으면 `set` 으로 진척률을 올린다. 그날 무엇이 됐는지 메모를 한 줄 붙인다.
   - 요약에는 있는데 항목이 없는 작업이면 `set` 으로 새 항목을 만든다.
   - 커밋으로 완료가 확인된 것만 100% 로 올린다. 화면이 하나 더 남았거나 "1차" 라고 적힌 커밋은 미완이다.
   - 진척률은 커밋에서 읽히는 범위로만 판단한다. 근거가 약하면 보수적으로 잡고, 정말 모르겠으면 그 항목만 사용자에게 묻는다.
2. 명령은 보고일 섹션에 적용되도록 `--date=<보고일>` 을 붙인다(보고일이 오늘이면 생략 가능).

   ```bash
   node wf.js progress set "모바일 앱 - 주문 관리 탭 구현" 60 "목록·상세·결제 화면 구현" --date=2026-09-10
   ```

3. 갱신이 끝나면 `node wf.js progress --date=<보고일>` 로 그날 섹션을 다시 읽어, 작업 요약 뒤에 `---` 한 줄을 두고 **한 글자도 바꾸지 않고** 그대로 붙인다(`[날짜]` 헤더는 빼고 항목만). 이 블록은 별도 양식으로 전달되는 글이라 형식(`제목 - N%`, 하위 `- 메모`)이 그대로여야 한다. 바뀐 항목만 추리지 않는다 — 그날의 전체 상태를 붙인다.

커밋이 없는 날은 갱신할 근거가 없으므로 `progress.md` 를 건드리지 않고, `wf daily` 가 이미 붙여 준 블록을 그대로 출력한다.

## 원칙

- **사실 우선.** 커밋에서 확인된 것만 쓴다. 없는 효과(속도·보안 향상 등)를 지어내지 않는다. 미완인 작업은 미완이라고 쓴다.
- **독자가 아는 말로만.** §4 의 판정을 매 항목에 적용한다 — 저장소를 열어봐야 아는 말이 하나라도 남아 있으면 그 항목은 아직 덜 고쳐진 것이다.
- **압축이 일의 핵심.** 모든 커밋을 살리려 하지 말고 주제로 묶어 짧게. 원본 커밋 메시지보다 읽기 쉬워야 한다.
